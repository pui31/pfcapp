# PFCApp — Kids App CANON

## 目的

子ども向けPFCAppはダイエットアプリではなく、食べ物の特徴を知り、自分の食事状態を見て「次に何を食べるか」を本人が考える力を育てる食育アプリである。

最終的な成功は、アプリがなくても食品の特徴や食事バランスをある程度自分で判断できるようになること。

## UX原則

- 食品を「良い／悪い」で評価しない。
- 食べた量やPFCの状態を、成功／失敗として採点しない。
- **PFCAppは数値の状態を見せる。状態を採点しない。**
- 厳密な一点目標や超過警告より、目安となる参考ゾーンと現在位置を見せる。
- アプリが毎回「次はこれを食べよう」と正解を指示せず、本人が状態から考える余白を残す。
- 記録漏れを失敗扱いしない。
- 成人向けダイエットのようなカロリー赤字、減量目標、運動消費との相殺を導入しない。
- 本人が食べたい日・量そのものを抑制することを目的にしない。
- 親による常時監視を主目的にしない。
- 記録の精密さそのものを目的にしない。多少の量のズレより、迷わず記録して食品の特徴と今日の状態を考えられることを優先する。

特に重要な利用タイミングは食後の反省ではなく、夕食前など「次に食べるものを考える前」である。

## MVPで検証する核

最初に検証するループは以下。

1. 食品を登録する。
2. 食品のP / F / Cの特徴を星で見る。
3. 今日のP / F / Cの現在位置が物差し上で動く。
4. 本人が星と現在位置を材料に、次に何を食べるか・どのくらい食べるかを考える。

食品図鑑、特徴カード、ゲーム報酬、AI写真認識、バーコード、学校給食専用入力、週間分析などは、この核の成立確認より後に実装してよい。

## MVP画面

初期実装は以下の2画面を中心とする。

1. Today / PFC状態
2. 食品追加

独立した食品詳細画面・履歴画面はMVPでは作らない。

## Today画面

### 基本構成

- 画面上部に日付を控えめに表示する。「きょう」という見出しは不要。
- 主役はP / F / Cキャラクターと今日の3本の物差し。
- その下に今日登録した食品一覧を表示する。
- 画面下部に `＋ 食べものを選ぶ` ボタンを固定する。
- Today画面自体は通常スクロールとし、PFC物差しは固定しない。

新しいローカル日付はP / F / Cすべて0から始める。昨日の状態による補正・繰り越し・評価は行わない。

MVPではオンボーディング／チュートリアルUIを必須としない。0件・0メモリは通常状態として静かに表示し、不足や行動指示を出さない。

### 今日の食品一覧

今日食べたものを思い出せることはMVPに必要である。

- 全件を縦に表示し、「もっと見る」等で件数制限しない。
- 新しい記録を上に表示する。
- 同じ食品を複数回登録しても統合せず、別記録として残す。
- 重複登録の警告は出さない。
- 各記録には食品名、量ラベル、P/F/C星を表示する。
- 「ふつう」の場合は、食品ごとの子ども向け基準量も併記できる。例: `ふつう（4枚くらい）`。
- 小分類アイコンを視覚的な目印・賑やかしとして表示する。カテゴリ名の文字表示は必須としない。

記録をタップした場合、独立した詳細画面へ遷移せず、小さな操作カード／メニューを開く。そこから `この記録を取り消す` を選択でき、実行前に軽い確認を1回挟む。スワイプ削除はMVPでは不要。

取り消し後は、その記録の実PFC値を合計から引き、物差しを滑らかに元の位置へ戻す。

## 食品入力

MVPの基本入力は以下。

`カテゴリ → 食品 → ちょっと / ふつう / いっぱい`

量ラベルは全食品共通の固定倍率ではなく、食品ごとに家庭内の実感に合う量を定義する。

### 量の考え方

`ちょっと / ふつう / いっぱい` は厳密な数量区分ではなく、ざっくり自己判断するための幅として扱う。

子ども向けに具体量を明示するのは原則として「ふつう」の基準量だけとする。

例:

- クッキー: `ふつう（4枚くらい）`
- ごはん: いつもの茶碗1杯程度を「ふつう」とする。
- 鮭: `ふつう（1切れくらい）`

「ちょっと＝何枚まで」「いっぱい＝何枚以上」のような境界は子ども向けUIに明示しない。1枚なら本人が「ちょっと」、8枚なら「いっぱい」等、近いと思うものを選べばよい。厳密な量を再現するために複数回登録したり、割合を計算したりする入力体験を要求しない。

「いっぱい」は悪い量を意味しない。単にその食品として多めの量を表す。

内部計算用の実量と、子ども向け「ふつう量の目安」は別の項目として扱う。

### 食品追加画面の構造

画面は大きく3領域で構成する。

1. 上部: 固定されたコンパクトなP/F/Cミニ物差し。
2. 中央: カテゴリタブと食品一覧。ここがスクロールする。
3. 下部: 食品選択・量選択・星・`追加する` を扱う固定パネル。

未選択時の下部固定領域は薄く保ち、食品を選択するとパネルが展開する。

量未選択でも `追加する` ボタン自体は表示するが無効状態とする。量を選択すると星と未来プレビューが表示され、ボタンが有効になる。

食品を選択しただけでは量を自動選択しない。「ふつう」を初期選択することも避ける。

量を切り替えると星と未来プレビューは即時更新する。食品を選び直した場合は量を未選択へ戻す。カテゴリを切り替えた場合は食品・量・星・未来プレビューをリセットする。

登録後はTodayへ戻る。次回食品追加画面を開く際はカテゴリ・食品・量をすべて未選択の初期状態から始める。

### カテゴリ探索

カテゴリはアコーディオンではなく、位置の変わらないタブ型UIとする。カテゴリタブの下にある食品表示エリアだけを切り替える。

カテゴリの基本順:

- 主食 🍚🍞🍜
- おかず 🥩🐟️🍟🥚
- 野菜・果物 🍅🥝
- おやつ 🍰🍪🍨
- その他 🍲

カテゴリ内では、小分類を `アイコン＋小分類名` の見出しとして使う。小分類自体は追加の操作ボタンにせず、その下に該当食品を直接並べる。

例: おかず内に `🥩 お肉`、`🐟️ お魚`、`🍟 揚げ物`、`🥚 たまご` 等。

食品ボタンはMVPではまず2列グリッドを実装候補とし、実機で長い食品名の改行・高さ・読みやすさを確認して列数等を調整してよい。2列は固定CANONではなく検証仮説とする。

既存食品データ上の小分類名 `お肉・揚げ物` は `揚げ物` へ統一する。

### 試して戻る

Todayから食品追加画面へ入るボタンは `＋ 食べものを選ぶ` とする。これは既に食べたものの記録だけでなく、「これを食べたらどうなるか」を試す入口でもある。

食品追加画面では左上の戻る操作でいつでもTodayへ戻れる。選択途中で戻っても破棄確認は不要。`追加する` を押したときだけ記録を確定する。

## 食品追加画面の未来プレビュー

食品追加画面上部のコンパクトなP/F/C物差しは、食品を選びながら今日の現在状態を見失わないために固定表示する。Todayの物差しより薄く簡潔で、目盛りを省略してよい。

量を選択したら、現在位置を残したまま、その食品を追加した場合に増える部分だけを別表現で重ねて未来位置をプレビューする。追加予定部分は黄色系の点滅／パルス等で区別する案を基本とするが、P/F/C固有色や警告色と混同しないよう実装時に調整する。

食品付近の星は「今回選んだ量の食品特性」、上部ミニ物差しは「今日の状態に加えたらどう動くか」を担当し、役割を重複させない。

未来プレビューは推薦・判定ではない。どの量を選ぶべきかはアプリが指示しない。

## 子ども向けPFC表示

子どもにはP / F / Cのグラム数を基本表示しない。

P / F / Cの文字自体を、丸く太い字体を基調とした小さなキャラクターとして扱う。目を付ける、瞬きする、登録時に軽く反応する等の生き物らしさは持たせてよいが、現在値に応じて悲しい／喜ぶ等の評価表情へ変化させない。

栄養素名は `たんぱく質 / 脂質 / 炭水化物` と漢字で表示し、将来実際の栄養成分表示を読む際の橋渡しとする。

P / F / Cの基本色方向は以下。

- P: ニュアンスのある赤系
- F: ニュアンスのある黄系
- C: 青〜水色系

原色そのものに固定せず、正確な色値はビジュアル実装時に調整する。色だけに識別を依存しない。日本の食育で使われる赤・黄・緑の食品群との混同、とくに `C=緑` や状態警告としての赤黄緑を避ける。

食品のP / F / Cを星（メモリ単位）へ翻訳し、今日の状態を同じ単位感で理解できるようにする。

### 星 / メモリ換算

現時点のMVP採用値:

- P: 5g = 1メモリ
- F: 5g = 1メモリ
- C: 15g = 1メモリ

食品の星数は原則として四捨五入で求める。ただし微量成分が丸めによって消え続けることを避けるため、☆0（ほぼなし）の範囲を別に定義する。

- P: 2g以下 → ☆0（ほぼなし）
- F: 1g以下 → ☆0（ほぼなし）
- C: 5g以下 → ☆0（ほぼなし）

上記を超える場合は、四捨五入結果が0でも最低⭐1として表示する。

表示例として、1〜5は通常の星を並べる。6以上は5個単位を「5を内包した大きな星」等の束記号にまとめる案を採用候補とする。実際のグリフ／見た目は実装時に調整してよいが、子どもが「5個分」と理解できることを優先する。

### 現実の栄養量との関係

丸め誤差によって食べた栄養量が消えないよう、内部のPFC集計は実際のg値を保持・累積する。

星は食品の特徴とメーター移動量を予測するための子ども向け翻訳表示であり、内部データそのものを整数星だけに置き換えない。

## 今日のPFC物差し

P / F / Cは、100%到達を目指すプログレスバーではなく「一本の長い物差し」として表示する。

現在位置は0から現在値までP/F/Cそれぞれの固有色で塗る。参考ゾーンは背景側に置く。

Today画面では物差し感が分かる目盛りを表示する。数値・g表示は原則不要。食品の星と物差しのメモリ感がつながることを優先する。

基本表示は各20メモリとする。

- P: 20メモリ = 100g
- F: 20メモリ = 100g
- C: 20メモリ = 300g

20メモリは達成上限ではない。超えた場合も「満タン」「失敗」とせず、現在位置がさらに先へ進んだことを表現する。

MVPでは20を超えた際に25、30…等へ表示範囲を段階的に拡張し、横スクロールを使わず試す案を実装仮説とする。ただしスケール圧縮により「20を大きく超えた」感覚が弱くならないか実機で検証する。見づらい場合は、目盛り幅を固定してPFC物差し領域だけを横スクロールする方式へ変更する。

### 参考ゾーン

MVPの初期参考ゾーン:

- P: 8〜14メモリ（約40〜70g）
- F: 8〜11メモリ（約40〜55g）
- C: 14〜18メモリ（約210〜270g）

子ども向け画面では原則としてgや数値ラベルを表示せず、参考ゾーンの位置と現在位置を空間的に見せる。

参考ゾーンの境界は鋭い箱ではなく、柔らかいぼかし・グラデーション等で「だいたいの目安」であることを表現する。

P / F / Cで参考ゾーンの位置が揃っていなくてよい。むしろその違いから「炭水化物はしっかり食べてよい」など、栄養素ごとの量感覚が育つことを期待する。

### 警告・色・演出

- 参考ゾーンへ入っても達成演出をしない。
- 参考ゾーンを越えても赤・オレンジ等の警告色へ変更しない。
- 「オーバー」「食べすぎ」「不足」「もう少し」「いい感じ」等、現在位置を評価する言葉を基本表示しない。
- 物差しの色は現在位置に関係なく一定とする。
- 参考ゾーンの前・中・後でキャラクター表情を変えない。

食品登録後はTodayへ戻り、旧位置から新位置へ物差しを滑らかに動かす。動いた先端付近に軽いキラキラ等を出してよい。これは「成功」の演出ではなく、登録によってどこが動いたかを伝える視覚フィードバックであり、参考ゾーンへの到達・超過とは連動させない。

本人が「今日はFが多そう」等を自分で読み取れることを狙う。

## 星と物差しの学習関係

食品の星と今日の物差しは、同じメモリ単位として理解できることを重視する。

例:

- 食品のFが⭐5なら、Fの物差しがおおむね5メモリ分進むと予想できる。
- 「ふつう」では参考ゾーンを越えそうだが、「ちょっと」ならどうか、という量の比較に使える。

ただし内部では実g値を保持するため、表示上の星は理解しやすい近似である。UIでは予測と実際の動きが直感的に矛盾しないよう調整する。

## 日付・記録単位

MVPでは朝／昼／晩／おやつ等の食事カテゴリを入力させない。Today一覧は食事時刻順を厳密に再現するものではなく、登録順を基本とする。まとめて後から登録した結果、実際の食事順と異なっても許容する。

将来必要性が確認された場合、食事カテゴリは必須入力ではなく任意タグとして再検討できる。

記録日は `登録した時刻のローカル日付` とする。前日を選んで登録する機能はMVPでは不要。

アプリを開いたまま日付が変わっても、強制的にTodayへ戻したり画面状態をリセットしたりしない。次の登録等、必要な操作時に現在のローカル日付を確認し、その日へ記録する。登録後にTodayへ戻った際は新しい日の状態が自然に表示される。

過去日の記録は将来の履歴・週間機能に備えて日付単位で内部保存してよいが、MVPで過去日UIを提供する必要はない。

## 食品マスタのMVP範囲

MVPは用意した固定食品マスタで運用し、アプリ内の親向け食品追加・編集UIは作らない。

食品が見つからない場合は、家庭内で「一番近い既存食品」を口頭で選ぶ運用を許容する。どうしても必要な食品はコード／データ側へ追加してアプリを更新する。

初期食品データは従来59食品を基礎とし、追加漏れとして `卵焼き` と `ゆで卵` を追加するため、少なくとも61食品となる。PFC値・家庭基準量は食品データ整備時に確定する。

既知のデータ修正事項として、枝豆のさや込み重量解釈、スープ類のレシピ全量基準への補正がある。

## データ保存・操作のMVP方針

- 個人の食事記録は端末ローカルに保存する。
- MVPでは認証・バックエンド・クラウド同期を必須としない。
- 再読み込み／アプリ再起動後も確定済み記録は残す。
- 食品追加途中の選択状態は永続化しない。
- 端末側のサイトデータが削除された場合のクラウド復旧はMVP対象外。
- `追加する` の多重操作による意図しない二重登録を防ぐ。

## 栄養基準の扱い

参考ゾーンは医療的な摂取上限や減量制限として扱わない。

年齢・性別等に応じた公的な食事摂取基準を参考にするが、体重や肥満度を理由として子どもの摂取上限を独自に引き下げる設計にはしない。

MVPで体重・肥満度の入力を必須にしない。

## 将来機能

### 自分で探す食品探索

アプリが「これを食べよう」と推薦する代わりに、本人がP / F / Cを探索軸として食品を探せる機能を将来候補とする。

例: `Pちゃん → 多め / 少なめ → 該当する食品を見る`。

これは「低いほうが良い」等の評価ではなく、本人が現在状態を見たうえで欲しい特徴を選び、食品を探索するための機能とする。

### 食品図鑑・特徴カード

新しい食品との出会い、食品の特徴、EPA/DHA・カルシウム等の語彙との初遭遇を作る仕組みを検討する。

### ゲーム報酬

本人から、何らかの達成に応じてアイコン・キャラクター等をプレゼントされる仕組みへの希望がある。

報酬機能自体は将来実装候補とする。ただし、以下のような条件は中心思想と衝突するため避ける。

- PFCを参考ゾーン内に収めたら成功報酬
- 超過しなかったら報酬
- 食事量を減らしたら報酬
- 連続記録できなければ報酬を失う

報酬条件は、探索・発見・食品を知ること・自分で考えること等、食育上の学習体験に結びつける方向で後日慎重に設計する。

## MVP技術方針

初期実装はPWAとする。

技術スタックの第一候補:

- TypeScript
- React
- Vite
- PWA

まず家庭内で素早く使えることを優先し、初期段階ではローカルのみ・認証なし・バックエンドなしでよい。

個人の食事ログを外部へ送信しない構成をMVPの基本とする。アプリコード／固定食品マスタの公開可否と、個人の食事データの秘匿性は分けて考える。

静的ホスティングとしてGitHub Pagesを有力候補とし、Git pushから自動デプロイできる運用を目指す。公開サイトの場合、検索エンジンへの `noindex` は補助策でありアクセス制御ではないことに注意する。ホスティングの最終的な実装HOWはコード／デプロイ設定を正本とする。

PWAのService Worker更新により古いアプリが残り続けないよう、更新挙動を意図的に設計する。

技術詳細は実装状態に応じてリポジトリ側を正本とする。
